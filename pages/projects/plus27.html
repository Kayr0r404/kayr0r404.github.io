PROJECT CASE STUDY · COMMUNITY PLATFORM

Plus27

An area-first community platform bringing local conversations, groups, events and services into one application.

Problem and product scope

Community activity is often spread across disconnected channels. Plus27 brings community discussions, groups, jobs, rentals, vendors and marketplace experiences into one product with a shared identity layer.

Architecture

Next.js App Router · React · TypeScript
↓ HTTPS / JSON API
FastAPI application · /api/v1
↓
User & authentication routers
↓
Shared auth · route guards · repository factory
↓
PostgreSQL (SQLModel / SQLAlchemy) · MongoDB (Beanie)

The backend is currently structured as one FastAPI application with separate user and authentication routers, rather than independent deployable microservices. A repository factory selects the user data implementation, with PostgreSQL and MongoDB persistence adapters.

Docker Compose provisions PostgreSQL and MongoDB for local development. The Java/Javalin directory is starter scaffolding and is not represented as an active application service.

Technology and responsibilities

  • Frontend: Next.js App Router, React, TypeScript and Tailwind CSS.
  • API: FastAPI with versioned user and authentication routes.
  • Identity: JWT access/refresh tokens, password hashing, cookie-based sessions and route-level guards.
  • Persistence: SQLModel/SQLAlchemy with PostgreSQL and Beanie with MongoDB.
  • Local infrastructure: Docker Compose for database services.

Architecture decisions worth explaining

Keeping HTTP routing, identity logic, repository selection and persistence in distinct modules makes the backend easier to evolve. The dual-database setup is an explicit design choice in the repository: user records can be routed through a selected repository implementation, while SQL and document models serve different data needs. It also adds operational complexity, so database ownership and consistency rules need to remain clear as the product grows.

My contribution
